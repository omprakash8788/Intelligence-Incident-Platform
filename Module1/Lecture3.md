### Lecture 3 — Production-Grade Error Handling

Today we're going to build the `error architecture` that every serious backend needs.

Our goal is:

```
Request
   ↓
Route
   ↓
Controller
   ↓
Service
   ↓
Error
   ↓
Global Error Middleware
   ↓
Consistent JSON Response
```

And we'll make sure one error `format is used throughout the entire system.`

---

### 1. The problem with normal Express errors

Suppose later we have:

```
throw new Error("Incident not found");

```

Without proper handling, we could end up returning inconsistent responses:

```
{
  "error": "Something went wrong"
}
```

or:
```
{
  "message": "Incident not found"
}
```


We want every error to look predictable:

```
{
  "success": false,
  "error": {
    "code": "INCIDENT_NOT_FOUND",
    "message": "Incident not found"
  }
}
```

---

### 2. Create AppError

Create:

```
src/errors/AppError.ts
```

```

export class AppError extends Error {
  public readonly statusCode: number;
  public readonly code: string;

  constructor(
    message: string,
    statusCode: number,
    code: string
  ) {
    super(message);

    this.name = "AppError";
    this.statusCode = statusCode;
    this.code = code;

    Object.setPrototypeOf(this, new.target.prototype);
  }
}

```

Now we can create application-level errors.

For example:

```
new AppError(
  "Incident not found",
  404,
  "INCIDENT_NOT_FOUND"
);

```

---

### 3. Why not just use Error?

Normal JavaScript:

```
throw new Error("Incident not found");
```

only gives us:

```
message
name
stack
```

But an HTTP API also needs:

```
HTTP status
application error code
```

So:

```
Error
 │
 ├── message
 ├── name
 └── stack

AppError
 │
 ├── message
 ├── name
 ├── stack
 ├── statusCode
 └── code

```

This gives our application structured errors.

---

### 4. Create specific errors

Create:

```
src/errors/NotFoundError.ts
```

```
import { AppError } from "./AppError.js";

export class NotFoundError extends AppError {
  constructor(
    message = "Resource not found",
    code = "RESOURCE_NOT_FOUND"
  ) {
    super(message, 404, code);
  }
}

```

Now we can write:
```
throw new NotFoundError(
  "Incident not found",
  "INCIDENT_NOT_FOUND"
);
```

Much cleaner.

### 7. Global Error Middleware

Now we need something that catches these errors.

```
src/middleware/error.middleware.ts
```

```
import { Request, Response, NextFunction } from "express";
import { AppError } from "../errors/AppError.js";

export const errorMiddleware = (
  err: unknown,
  _req: Request,
  res: Response,
  _next: NextFunction
) => {
  if (err instanceof AppError) {
    res.status(err.statusCode).json({
      success: false,
      error: {
        code: err.code,
        message: err.message
      }
    });

    return;
  }

  console.error(err);

  res.status(500).json({
    success: false,
    error: {
      code: "INTERNAL_SERVER_ERROR",
      message: "Internal server error"
    }
  });
};
```

---

### 8. Why unknown?

Notice:

```
err: unknown

```
instead of:
```
err:any
```

This is intentional.

TypeScript forces us to verify what the error actually is.

For example:

```
if (err instanceof AppError)

```

Now TypeScript knows:
```
err = AppError
```

and therefore allows:

```
err.statusCode
err.code
err.message
```

This is safer than blindly trusting `any`.

---

### 9. Register the middleware

Modify:

```
src/app.ts
```

to:

```
import express from "express";
import healthRoutes from "./routes/health.routes.js";
import { errorMiddleware } from "./middleware/error.middleware.js";

const app = express();

app.use(express.json());

app.use("/health", healthRoutes);

app.use(errorMiddleware);

export default app;

```

### Important

Error middleware should be registered `after your routes`.

```
Middleware
     ↓
Routes
     ↓
Error Middleware
```

Why?

Because errors generated by the routes need to travel to the error middleware.

### 10. Create a test endpoint

We need a way to intentionally generate an error.

Modify:

```
src/routes/health.routes.ts
```

temporarily:

```
import { Router } from "express";
import { healthController } from "../controllers/health.controller.js";
import { NotFoundError } from "../errors/NotFoundError.js";

const router = Router();

router.get("/", healthController);

router.get("/test-error", () => {
  throw new NotFoundError(
    "Test incident does not exist",
    "INCIDENT_NOT_FOUND"
  );
});

export default router;
```
Now run:

```
npm run dev
```

Open:
```
GET /health/test-error
```

Expected:

```
{
  "success": false,
  "error": {
    "code": "INCIDENT_NOT_FOUND",
    "message": "Test incident does not exist"
  }
}

```

This is our first proper centralized error flow.

---

### 11. What just happened?

The request:

```
GET /health/test-error
```

went through:

```
HTTP
 ↓
Express
 ↓
health.routes.ts
 ↓
throw NotFoundError
 ↓
Express error pipeline
 ↓
errorMiddleware
 ↓
JSON response

```

This pattern becomes extremely important when we eventually have:

```

API
 │
 ├── Incident Service
 ├── Event Service
 ├── Metrics Service
 └── Queue Service

```

All of them can use the same error architecture.

### 12. Unknown errors

Now let's test a normal JavaScript error.

Add temporarily:

```

router.get("/test-unknown-error", () => {
  throw new Error("Database exploded");
});

```

Call:

```

GET /health/test-unknown-error

```

You should receive:

``` 

{
  "success": false,
  "error": {
    "code": "INTERNAL_SERVER_ERROR",
    "message": "Internal server error"
  }
}


```

But your server console should contain the actual error:


```
Error: Database exploded

```

This distinction is important.

##### Client sees:
```
Internal server error

```

#### Server logs:
```
actual technical error

```

We don't expose internal implementation details to clients.

---

### 13. Security principle

Never do this in production:
```
res.status(500).json({
  error: err
});
```

Because an error might contain:
```
database connection string
filesystem path
SQL query
internal service name
stack trace
credentials
```

Instead:
```
Client
  ↓
Safe error message

Server
  ↓
Detailed logs
```

Later we'll build proper structured logging.
